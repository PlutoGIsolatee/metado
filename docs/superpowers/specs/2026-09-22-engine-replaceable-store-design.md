# Metado 引擎可替换与状态所有权（增补设计）

日期：2026-09-22
状态：待评审
基线：`2026-09-18-metado-design.md`（rev 10）；`2026-09-21-real-execution-chain-design.md`
关系：本增补**新增并修订**主文档相关章节；发生冲突时，经评审后以本增补为准。

> **声明：本文所有实现示例仅供示意，保证接口语义一致即可；具体命名与形态以实现为准。（与主文档一致）**

## 1. 定位与目标

- **动机**："引擎可定制"（主文档 §8.1）与"宿主/引擎脱耦合"（§11）的自然延伸——把脱耦推到逻辑终点：**引擎实现本身成为宿主可替换的组件**。
- **目标**：
  1. 宿主可**整体替换**引擎（产物/版本），插件、授权、storage、身份记录**无缝延续**；
  2. 引擎**每次启动从已有数据读取**，自洽恢复，不依赖宿主输入；
  3. 宿主只面对契约（IPC + 能力），state 对宿主**黑盒**。

## 2. 权威划分（修订 §11.4）

两个正交的轴：

- **决策权威**：谁产生治理决定 → **始终宿主**（命令源）。
- **状态所有权**：谁持有并持久化结果 → **引擎**。

修订后：

| | rev 10 | 本增补 |
|---|---|---|
| 引擎 | 无主见执行者（裁决 / 沙箱 / 能力机制） | + **状态所有者**：持久化 engine/state.json、启动读 state、单写者、原子替换、自主状态落盘 |
| 宿主 | 决策与管理 | **决策权威 + 命令源 + 观测**；"管理"缩为"决策 + 经 RPC 下发"；**永不直接读写 state** |

推论：

- 授权跨重启 / 换代**延续**，宿主无需重灌；
- 宿主重启、引擎替换均对宿主无感；
- 管理面 RPC 不变，只是语义上"决策落引擎、状态归引擎"。

## 3. 可信域与安全

- **可信域 = 宿主 + 引擎 + 引擎数据目录（含 state）**，同一可信域，OS 层文件权限即可；state **不签名、不加密**——能改 state 者也能改引擎本身，防护无意义。
- **插件是不可信方**；唯一要守的一条：**插件碰不到 state**（呼应 §11.1——造假面不在本地管道，插件签名面才是外界信任边界）。三条机制：
  1. 插件只能经**受治理的能力面**访问**被授权的数据域**：私有 `<plugin_id>` 分区始终属本插件；共享 `<signer_id>` 分区需显式授权（`storage.<signer>.*` / `vfs.<signer>.*` 等），未声明不可达。各持久化能力（storage / vfs）都是同一低层持久化原语之上的受 scope 视图，一律过权限放行，**无特权通道**；
  2. state 文档与 plugins/ 与 shared/ 根目录在**任何能力面、模块文件系统里不可达**；
  3. 模块文件系统只读、不挂载 state。
- **信任决策不落 state**："信不信该 signer"是宿主决策、非引擎事实；引擎落盘的只有 `granted` 等**事实**。

## 4. 架构

```
┌────────────────────────────┐
│          宿主（app / CLI）    │  决策权威 + 命令源
│  信任 / grant / config / 生命周期命令   │  永不直接读写 state
└────────────┬───────────────┘
             │ JSON-RPC 管理面 / 回调面
             │ （宿主侧契约 = IPC 协议 + 能力契约；state 对宿主黑盒）
             ▼
┌────────────────────────────┐        ┌────────────────────────────┐
│         引擎进程            │  读写   │      引擎数据基目录           │
│ （可替换产物；宿主选中启动；   │ ─────► │  engine/state.json            │
│  命令行/环境传入 state 路径）  │        │    + plugins/ + shared/      │
│                            │        └────────────────────────────┘
│  状态所有者 + 执行者 + 自主状态 │
└────────────┬───────────────┘
             │ 引擎间契约 = state 格式（替换专用；引擎↔引擎，宿主黑盒）
             ▼
        另一引擎产物（停旧起新，指同一 state 即无缝接管）
```

要点：

- 宿主直接启动引擎进程，选定产物并传入 state 路径（命令行 / 环境）。
- **替换 = 停旧 + 起新 + 指同一 state**；新引擎读同一份数据接着推进。
- **单写者**：同一时刻一个 state 只服务一个引擎实例（引擎启动以 state 文件锁强制）。
- 引擎交互仅经 IPC（管理方法面 + 回调面），进程绝对独立（§11 不变）。

**契约三件套**：

1. **IPC 协议**（宿主 ↔ 引擎）；
2. **state 格式**（引擎 ↔ 引擎，宿主黑盒）；
3. **能力契约**（capability 名 / 形状）。

## 5. state 文档模型

### 5.1 物理分离

```
引擎数据基目录
  ├─ engine/                       ← 引擎自身数据（state.json，原子替换、独立机制）
  │   └── state.json
  └── plugins/                     ← 插件数据域（低层存储原语 + 数据）
       ├─ <plugin_id>/             ← 每插件一个目录
       │   ├── meta.json           ← 不可变元数据锚点
       │   ├── private/            ← 私有 keyspace
       │   │   ├── kv/
       │   │   ├── vfs/
       │   │   ├── tmp/
       │   │   └── cookie/
       │   └── bundles/            ← 插件本体（原样 .mdl）
       │       └── <version>.mdl
       └── shared/                 ← 共享 keyspace（按 signer_id，顶层）
           └── <signer_id>/
               ├── ownership.json  ← 前缀归属标记
               ├── kv/
               └── vfs/
```

- **引擎本体数据与插件数据物理及机制分离**：engine/state.json 用引擎自身简单原子文件机制（写临时文件 → rename）；**低层持久化原语只管 plugins/ 与 shared/ 域**。
- **低层持久化原语非唯一**，供内置能力复用（storage / vfs 同待遇，storage 不特殊）；**其具体形态与具体内置 API 一并推后**（见 §13）。
- 物理分离收益：插件数据爆炸 / 损坏 / 限额不波及引擎状态；卸载 / 清库只动 plugins/ 与 shared/；engine/state.json 根本不在插件数据文件域内（能力边界之外再有文件树隔离）。
- `volume_ref`（state → 插件数据卷）引用关系由 engine/state.json 记录。

### 5.2 命名空间 + 字段

- state = **自描述文档**（文本先行，二进制化推迟），结构 = **命名空间 + 字段**。
- **命名空间 = 引入该字段的引擎分支（lineage/fork）标识符**；字段随分支归属，任何引擎只能往"自己分支的根"下加字段，不得写入他人分支根。
- 具体分支 id 的**唯一性机制暂不约束**（待补，§13）。
- 内容骨架（trunk 公共底）——**只含不可重算的决策事实、引用与状态**：

```
metado.format_version            ← 主版本（语义变更的唯一门闩）
metado.plugins.<id>
   state / lifecycle_effective   ← 状态与宿主决策
   bundle_ref                    ← 原样 .mdl 本体位置
   volume_ref                    ← 内置 API 数据卷位置
metado.grants.<id>               ← granted ⊆ requested（宿主决策）
metado.permission_sets.<name>
metado.domain.<rule>
branch.<branch-id>.*             ← 分支扩展命名空间（互不干扰）
```

- **可重算数据一律不持久化**：`signer_id`（公钥指纹）、version、requested、entries、lifecycle 声明等全部可从插件本体（原样 `.mdl`）重算——**本体是唯一源**，state 不存镜像、不存首装指纹锚。启动/恢复按需拆包已装本体重建（v1 不压缩、ZIP 索引 O(1)，开销可接受；提速只能加"由本体哈希派生的缓存"，非契约）。
- **同签判据 = 与当前存储本体的 signer 比对**（重算）：引擎是唯一写者、bundle 只能经引擎入位，首装锚冗余——主文档 §6.2-3"按 plugin_id 保存首装指纹"字面据此修订。
- **不进 state 的**：`active`（引擎产物的启动配置，见 §7.1）；信任决策（§3）。

### 5.3 统一字段规则

- 认得 → 按语义用；**不认得 → 原样保留、绝不重写、绝不据此拒绝**（基础字段与扩展字段同一处理）。
- **只加不改**；字段含义变更 = 主版本 + 迁移，不在扩展性范畴。
- **主版本不认 → 拒绝启动**（唯一硬门闩）。
- **原子替换**：更新 = 写临时文件 → rename，单写者，崩溃安全。
- "基础 vs 扩展"的区分只在**语义权威**（trunk 有唯一权威定义，防扩展遮蔽串味），**处理方式完全一致**。
- 谁必须懂它：**只引擎**；宿主持有黑盒。

## 6. 启动时序

```
宿主选定引擎产物 → 启动（传入 state 路径）
├─ state 文件锁：拿不到（已有实例存活）→ 拒绝启动（单写者守卫）
├─ state 存在但不可解析 / 主版本不认 → 拒绝启动（fail-safe，绝不静默清空当新库）
├─ state 路径不存在 → 全新部署（空启动）
├─ 读取并重建：插件表、granted、permission-set、domain config
├─ 挂载卷（按 volume_ref；逐插件，坏卷置 error 上报，不拖垮整体）
└─ 服务 RPC（listPlugins / grant / invoke …）
```

- 引擎**自洽**：不依赖宿主任何输入即达一致状态。
- 温 realm 惰性创建（首次 invoke + boot 重水合，§7）。
- 写回仅发生在状态变化时，原子进行。

## 7. 生命周期

### 7.1 持久 vs 运行态

- **持久（state）**：身份记录（plugin_id / version）、`granted`、permission-set 定义、domain config、lifecycle effective。
- **运行态（重建，不落盘）**：loading、realm 创建 + boot、evicted、quarantine——quarantine 是"realm 不可用"的判定，realm 本是可重建缓存，重启即清。
- **`active`（引擎级）运行时不可变**：是引擎产物的**启动配置**（宿主启动时传入，与 state 路径并列），不进 state、不进替换契约。静态面每次部署确定，无"生效时点"问题。

### 7.2 状态模型

```
absent → installed（记录入 state；即刻可 invoke）
       → uninstalled（记录移除；数据默认保留，purge 删）
granted ⊆ requested：纯放行集合，非运行门槛（granted 空也可运行）
运行态全在 realm 层：无 realm / 温 / evicted / quarantine
```

- **可运行性 = installed；放行 = granted**。"能跑但没权限"是常态，不是异常。
- `pending` 状态**取消**（至多作展示标签"未授任何权限"，不载执行语义）。
- 权限语义随之归正：**缺权 ≠ 缺导出**（导出照静态面，调用才裁决）；插件装完即可 invoke，未授能力的能力调用一律 `PermissionDenied`。

### 7.3 转移表

| 动作 | state 变化 | 运行态 |
|---|---|---|
| `loadPlugin` | 记身份 + requested（pending 标签） | 可 invoke（未授能力调用 PermissionDenied） |
| `grant` | granted 增大（⊆ requested，越界拒绝） | 放行实时生效；导出不重建 |
| `revoke` | granted 缩小 | 放行实时收回；导出不重建 |
| `update`（同签） | 重记 version + requested；`granted ← 旧 ∩ 新` + 新项需显式 grant | realm 必重建 |
| `setLifecycle` | 写 state | 按规则 |
| `uninstall` / `purge` | 移除记录；purge 另删数据 | realm 弃 |
| 重启 / 换引擎 | 从 state 恢复 | realm 全重建、惰性 |

### 7.4 更新与版本

- **同签校验**：新 bundle 的 signer 必须等于**当前存储本体**的 signer（自本体重算比对），否则拒绝；引擎为唯一写者、本体只能经引擎入位，无须持久化首装锚（§6.2-3 字面据此修订）。
- `plugin_id` 变更 = **新插件**（新记录，不覆盖）。
- 更新失败（静态校验不过）→ **旧版原样保留**（原子写防半途）。
- **重装还原数据**：卸载默认保留私有卷；重装时旧 `<plugin_id>` 卷仍在 → `volume_ref` 指回旧卷（数据还原）；`purge` 掉则为新卷。
- 共享 signer 域不随单个插件清理（§7.5 不变）。

## 8. 边界情况汇总


| 边界 | 规则 |
|---|---|
| 实时放行 vs 冻结导出面 | 导出存在性在 realm 创建定格；grant/revoke 对运行中 realm 的放行**实时生效** |
| 静态导入可用之外 | realm 创建期的 ESM 链接失败（快速失败），与放行是两回事 |
| update 扩权 | `granted ← 旧 ∩ 新` 自动延续；新请求项需显式 grant（同签不能偷扩权） |
| quarantine | 不落盘；重启清；宿主只收 `notify` |
| 换代能力集缺失 | 插件请求的能力在新产物里没有 → 导出消失 / 不可用，正常；宿主选产物时承担 |
| state 缺失 vs 损坏 | 路径不存在 = 全新部署；存在但不可解析 / 主版本不认 = 拒绝启动 |
| 单写者 | 引擎启动取 state 文件锁；拿不到 = 已有实例 → 拒绝启动 |
| 重装还原 | 旧私有卷仍在 → volume_ref 指回旧卷；purge 则为新卷 |
| grant 越界 | `grant` 只接受 ⊆ requested，越界拒绝并报错 |
| 授予未 available 能力 | 允许存，但不产生导出（无害，调用时 link fail） |
| 同版本 / 降级 | 由 SemVer 门闩处理（§10） |
| 部分卷缺失 / 损坏 | 引擎整体照起，坏插件标记 error 上报，不拖垮全库 |
| 并发 | 引擎单事件循环 → grant/revoke 与 invoke 串行，无真竞态 |
| state 体积 | 小文档，原子替换成本随插件数线性；不做性能承诺 |

## 9. 权限模型重述（归正）

- **三层**（§5 不变）：请求（manifest）/ 授予（`granted ⊆ requested`，宿主运行时决定）/ **执行（每次调用，引擎执行层 `resolver.check(requested, granted, domain_rules)`）**。
- **静态面 = 导出存在性 = requested ∩ available（compiled ∩ active）**，realm 创建定格；**动态面 = 调用放行（granted + domain rules）**。
- **裁决归引擎**：不存在"宿主执行引擎授权"；宿主只提供决策输入（granted、domain config 值），不参与逐次裁决。
- 内置 API（`@metado/runtime` 面）与宿主 API（宿主能力实现 / 扩展）**不混**：后者走同一能力框架，与内置能力同待遇（§8.1），不便读作"引擎不为宿主 API 授权"。
- `active` 运行时不可变 → 静态面每次部署确定（§7.1）。
- real-execution-chain 计划中"宿主侧二次裁决"的表述**归正**为"引擎执行层裁决（CLI 内联）"。

## 10. 插件版本语义（SemVer 门闩）

- **仅**插件 manifest `version` 强制 SemVer；其职责**仅**为"是否执行更新"（排序门闩），**不承载授权 / 兼容 / 行为语义**——授权延续与版本号无关（§7.3 update 规则）。
- 规则：

| 情形 | 判定 |
|---|---|
| 版本语法非法 | load 失败 |
| 同签、版本 > 旧 | 允许更新 |
| 版本 == 旧 | 拒绝（视为重复） |
| 版本 < 旧 | 拒绝（回退不是更新；显式 uninstall + install 做） |
| 首次安装 | 无比较，记首装版本 |
| update 授权 | 与版本无关，走既定延续规则 |

- 允许 prerelease（`1.0.0-rc.1`），排序按标准 SemVer 优先级。
- 附带收益：同签同版本 = 拒绝，逼发布侧正确递增版本，避免"悄悄重发同版本"。

## 11. CLI / dev 影响

- **daemon**：本就是引擎进程，是 engine/state.json + 卷的家，无冲突。
- **CLI in-process 宿主**（§12.1）：为保行为对齐，`mdl run` 走**同一 engine/state.json 机制**，state 落在临时 / 工作目录（可 `--workdir` 指定），`--grant` / `--ask` 照旧写 state；生产差异只剩"授权决策者"（§12.4）。dev 实例可一键弃置。
- **real-execution-chain 计划修正两点**：① "宿主侧二次裁决"归正为"引擎执行层裁决（CLI 内联）"；② CLI 落工作目录 state。

## 13. 待补项（推后）

- `branch-id` 唯一性机制（暂不约束，`互不干扰`依赖分支自行合规）。
- 低层持久化原语具体形态（**非唯一**）+ 具体内置 API 一并推后。
- 具体能力 API / 值语义 / 错误 / 返回值编码（沿用主文档 §14 研究桶）。
- 信任决策的宿主侧接口与持久化归属（不落 state，具体接口另定）。

## 14. 已定结论速查

- 权威：宿主 = 决策权威 + 命令源；引擎 = 状态所有者 + 执行者 + 自主状态产生者。
- 可信：state 不加密不签名；防的是**插件**篡改，手段是能力面 + 文件树双隔离。
- state：自描述文档、命名空间 + 字段、统一处理、只加不改、主版本闩、原子替换、单写者。
- 物理分离：engine 独立；低层持久化原语只服务 plugins/ 与 shared/（非唯一、形态推后）。
- 生命周期：三态（absent / installed / uninstalled）+ granted 纯放行集；可运行性 = installed。
- 版本：插件 version 强制 SemVer，仅作更新门闩。
- `active`：引擎级、运行时不可变、启动配置、不进 state。
