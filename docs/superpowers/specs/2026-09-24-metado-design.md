## 1. 概述与目标

### 概述

Metado 是一个可嵌入、跨平台（Android / Windows / Linux）的 JavaScript 运行时，配套受治理的单文件插件打包格式。插件用标准 JavaScript（ESM）编写，TypeScript 源码经运行时编译后同样支持；以带签名的单文件 `.mdl`（二进制 ESM 模块树容器）交付，由引擎加载执行。

核心价值：细粒度权限治理（插件级最小权限、用户可设授予、领域细分权限、权限集）+ Android 式签名信任（完整性验签、签名即稳定身份、同签更新、同签名数据互通）。

一句话定位：能装进移动应用的小型、纯洁、可静态验证、带细粒度权限治理与签名信任的 JS 运行时。

### 目标

- G1 跨平台可嵌入：引擎以绝对独立进程/服务运行；引擎持久化状态实现可替换、自洽恢复
- G2 语言：标准 JS（ESM）为插件语言，TypeScript 经运行时编译支持；WASM 以双面内核集成——标准 `WebAssembly` 命名空间 + 直接 `.wasm` 模块导入（采纳演进中的 WASM ESM integration 草案，named exports = wasm exports），与 Vite 作者工作流、浏览器/Node 演进方向对齐
- G3 生态复用：插件源码 = 合法 Node 项目（除 API）——标准 npm 结构、Node 工具链直接可用；唯一例外——Node 核心 API 运行时不可用，一律以受治理的 metado 能力替代（仅白名单 shim：Buffer/path/events）；npm 纯 ESM 依赖可直接装入容器
- G4 能力 API：`@metado/runtime` 跨运行时契约，引擎内为内置虚拟模块、Node 内为真实 npm 包，同一源码双运行时；目标状态 Node 可运行 + 现有工具链完全可测试
- G5 权限治理一等公民：请求 / 授予 / 执行三层语义，最小权限、用户可设授予、领域规则可叠加
- G6 生命周期常驻治理：分级（声明 / 用户确认 / 可修改），正确性不依赖内存态
- G7 签名信任：Android 式体系——完整性验签、签名即稳定身份、同签更新、同签名数据互通
- G8 单文件发布：二进制模块树容器，零打包转换；多文件源码
- G9 生产可读可调试：无 minify/混淆，堆栈指向真实文件与行号
- G10 CLI 与生产行为对齐：单一引擎核心，快速迭代与热重载

### S1 标准追随（确定政策）

插件生态遵循并镜像演进中的 Web/Node 平台形状，选择性积极采纳**已形成共识、方向明确但未定稿**的草案能力（如 WASM ESM integration 的直接导入形状），与主流作者工作流对照；只镜像形状，不镜像权限语义。选择性由"安全、离线可测、与建模一致"三道闸约束，非盲目追新。

### 非目标（原则性永恒排除）

- 任何自定义脚本语法 —— 插件就是标准 JS/TS
- 代码转换/最小化/混淆 —— 分发物零转换、零 minify（TS→JS 的运行时编译是必要转换，不属此类）
- 引擎裁决"发布者可不可信" —— 信任决策在用户/宿主侧，引擎只验证不裁决
- 句柄式宿主对象跨入 WASM 计算内核

## 2. 约束与假设

### 干系人

- 插件开发者：编写插件，面对 manifest + `@metado/runtime` + mdl 工具链
- 宿主开发者：将引擎嵌入应用，定制能力集，做信任与授权决策的 UI
- 终端用户：安装/授予/削减/卸载的最终决策者（经由宿主 UI）
- 引擎维护者：演进引擎核心、能力框架与本设计文档

### 硬约束（外部给定，设计只能服从）

- C1 平台进程模型：iOS 无独立辅助进程 → 仅支持 Android / Windows / Linux
- C2 移动进程生命周期不确定：宿主负责按需拉起引擎进程，引擎正确性不得依赖内存常驻、自启动或长期存活保证
- C3 移动端资源有限：内存、包体积、CPU 受限 → 驱动执行预算、温 realm 缓存、可回收设计

### 假设（可被证伪）

- A1 本地信道可信：引擎-宿主 IPC 同设备，攻击面在插件签名而不在本地管道。
  证伪条件：同设备恶意进程可劫持 IPC 管道 → 需加密/鉴权。
- A2 信任域划分：宿主可信（与引擎同域），插件不可信。
  证伪条件：宿主不可信 → 授权与信任决策整体无意义。
- A3 执行器充分：BOA 的 JS/ESM 语义支撑插件模型（模块、async、错误）。
  证伪条件：BOA 缺口阻塞核心语义 → 换执行器或补齐。
- A4 用户确认可达：宿主具备向用户请求确认的 UI 能力（引擎从不等待用户）。
  证伪条件：宿主无 UI 通道 → 安装/授权确认流无法落地。
- A5 Ed25519 在实用意义上安全（无实际可行的伪造/密钥恢复攻击）。
  证伪条件：出现实际可行的攻击 → 触发 §9 签名算法升级议题。
  注：当前仅实现 Ed25519 是设计现状（信封已预留 algorithm 字段），不是硬约束。

## 3. 术语表

> 术语格式：可翻译术语写作「中文名（English）」，正文沿用中文名；保留原文术语（realm、granted 等）直接引英文，仅中文释义。全文一词一义；本表为全文档唯一权威映射。

### 3.1 术语状态约定

- **首选术语**：标准用词，全文档统一使用（默认状态，正文不标注）。
- **已承认术语**：可接受的同义词，允许使用但优先首选术语（仅首次出现处标注）。
- **已废弃术语**：不再使用，保留记录，指向替代术语。
- **已过时术语**：概念已过时、不再维护，保留历史记录，标注废弃原因。

### 3.2 现行术语（首选）

- **引擎（engine）**：执行插件、持有持久化状态的独立进程/服务；宿主可替换的组件。
- **宿主（host）**：嵌入引擎、做信任与授权决策的应用；决策权威与命令源，仅经 §7 IPC 交互。
- **插件（plugin）**：以 `.mdl` 交付的一段程序，manifest 声明权限与入口。
- **能力（capability）**：插件可调用的受治理 API 面（内置或宿主定制）。
- **realm**：插件的一次运行实例（加载解析后定格的授权视图 + 执行上下文）。
- **manifest（mdl.toml）**：插件声明文件（名称、版本、权限、入口、生命周期、依赖）。
- **requested**：manifest 声明的权限请求。
- **granted**：宿主运行时授予的权限集（granted ⊆ requested）。
- **available**：引擎在编译期 features 与 active 交集之下实际可用的能力面。
- **signer / signer_id**：签名者实体 / 其稳定身份；签名即身份。
- **同签更新（same-signer update）**：同一 signer 签发的新版本可更新旧版本。
- **同签名数据互通（same-signer data sharing）**：同 signer 的插件可访问彼此 storage 命名空间。
- **storage**：引擎持久化的插件数据（按 signer 命名空间隔离）。
- **state（engine/state.json）**：引擎自身持久化状态（安装记录等）；引擎间替换契约核心。
- **生命周期（lifecycle）**：插件常驻模式（声明 / 用户确认 / 可修改）。
- **uninstall / purge**：卸载（默认保留 storage）/ 彻底清除。
- **ED25519**：签名算法；其安全为前提假设（§2 A5）。
- **零转换**：分发物不经历打包转换，保留真实模块结构与源码。
- **@metado/runtime**：跨运行时能力 API 契约（引擎内置虚拟模块 / Node 真实 npm 包）。
- **白名单 shim（Buffer/path/events）**：Node 核心 API 形状兼容层，仅三个。

- 生命周期：常驻模式分级治理，正确性不依赖内存态（§7）

### 4.2 动态视图

三个代表性流程（完整时序与全部异常见对应章节）：

F1 安装与授权（宿主→引擎，命令源→状态所有者）：

```
宿主                    引擎
 │  loadPlugin(.mdl)──────►  验签 → 拆包 → 静态检查 → 落盘
 │◄────────────────────{plugin_id, signer_id, requested, lifecycle}
 │  setLifecycle(mode)───►  写 state（原子替换）

```

```
插件 realm              权限裁决              能力
   │  @metado/runtime ─────►  requested ∩ granted ∩
   │   能力调用                    domain rules 判定
   │  pass ◄─────────────────
   │  ▶ 能力执行（内置 / capability message→宿主服务）
```

F3 失败（ExecutionError 四域，§9）：realm 存活 → 宿主按业务处置；realm 判定 → 引擎 quarantine。

```
运行单元与进程边界：
┌─────────────── APK/AAB（宿主应用） ───────────────┐
│  宿主主进程（UI/信任决策，负责按需拉起引擎）        │
│      │  IPC（JSON-RPC 2.0）                        │
│      ▼                                             │
```

### 5.1 S1 引擎进程与可替换

#### 1 概述

- 标识：engine process & replaceability（图 S 顶层"引擎"框，§4.1）。
- 目的：引擎以绝对独立进程运行，自洽恢复，经唯一 IPC 面服务宿主的管理命令与回调，并承接"引擎实现可整体替换"的契约。
- 范围：进程生命周期与自洽恢复、IPC 服务（管理面 + 回调面）、引擎间替换契约、state 读入。不涉及插件执行、权限裁决等（分属 S3/S5）。
- 上下文位置：宿主（决策权威 + 命令源）与引擎数据基目录之间的唯一边界；插件生态经 loadPlugin 与引擎交互。

#### 2 职责与非目标

负责：
- 以独立进程运行；故障隔离（插件崩溃不拖垮宿主、宿主崩溃不拖垮引擎）
- 进程生命周期：启动读 state → 自洽恢复 → 服务；崩溃后由宿主按需重启
- 经 IPC 提供管理方法面（host→engine）与回调面（engine→host）
- 承接引擎替换：停旧 + 起新 + 指同一 state，插件/授权/storage/身份记录无缝延续

非目标：
- 不驻留任何宿主代码（运行期零注入，定制仅构建期 §8.1）
- 不自行保活、不自启动（宿主负责按需拉起，C2）
- 不裁决"发布者可不可信"（信任决策在宿主/用户侧）
- 不直接读写宿主数据；宿主也永不直接读写 state（ADR-001）

#### 3 对外接口

管理方法面（host→engine，JSON-RPC 2.0 line protocol）：

| 方法 | 语义 |
|---|---|
| loadPlugin(bytes) | 验签闸门 → 解析 → 静态检查 → 返回 {plugin_id, signer_id, requested, lifecycle} |
| grant / revoke(plugin_id, perms) | 授予（granted ⊆ requested）/ 削减 |
| setLifecycle(plugin_id, mode) | 设 effective 常驻模式（升级超出承诺由宿主先确认） |
| invoke(plugin_id, entry, value) | 调入口 → Result<Value, ExecutionError>；插件内排队 |
| listPlugins / uninstall / purge | 生命周期管理（uninstall 默认保留数据） |
| registerPermissionSet(name, perms) | 定义权限集 |
| setDomainConfig(ruleId, json) | 领域规则运行时配置（白名单/配额/降级） |
| trace 订阅 | 流式轨迹开/关 |

回调面（engine→host）：
- `dispatch(name, params, requestId)` → host 返回 Value/Error：capability message，app 驻留服务收到路由值、执行后 resolve 插件 promise（单次 Request-Response）
- `notify(event)`：事件流广播（见 §8）

线格式：JSON-RPC 2.0；大 blob 留引擎内不跨 IPC。transport：默认同机 Unix domain socket；需远程访问或兼容性问题时回退 TCP。错误：管理 RPC 失败 = JSON-RPC error 对象，与 invoke 的 ExecutionError 分线。

#### 4 内部结构

```
引擎进程
├── 进程主管（cold start：读 state → 自洽恢复；服务分发）
├── 管理方法实现（loadPlugin / grant / …，逐条转交对应子系统）
├── IPC 服务（transport 抽象：UDS/TCP；JSON-RPC 编解码）
├── 回调发射（capability message / 事件流，engine→host）
└── 引擎数据基目录访问（state 读入/原子替换；plugins/ 归 S7）
```

依赖：S7（state 契约 / 卷挂载）、S2/S3/S4/S5/S6（方法实现）；无宿主代码依赖。

#### 5 数据设计

- engine/state.json：引擎自身持久化状态（安装记录、授权、生命周期、volume_ref 等；全量契约见 S7 §5）；引擎间替换契约核心，宿主黑盒。
- plugins/（插件数据域，属 S7）：私有 `<plugin_id>/private/` + 共享 `shared/<signer_id>/`（低层持久化原语承载 storage/vfs 视图）；`bundles/<version>.mdl` 原样本体。本系统仅"访问"不"拥有"。
- volume_ref：非目录，是 state 内逐插件引用（state → 插件数据卷），启动时按它挂载，坏卷置 error 上报。
- 数据流：宿主命令 → IPC → 各子系统处理 → 变更沉淀回 state → 原子替换。

#### 6 关键流程与算法

进程级状态机：

```
            state 缺失───────────► 全新部署（空启动）
                 │
Cold start ──► 读 state ──► state 可解析且主版本认 ──► 挂载卷 → Serving
                 │                                          │
                 └─ 损坏 / 主版本不认 ──► 拒绝启动            ├─ 插件崩溃 → realm 回收，进程存活
                                              ▲              ├─ 进程被杀/崩溃 → 宿主重启
                                              │              └─ 引擎替换 → 停旧+起新+指同一 state
```

启动时序（详 §S7 §6）：state 文件锁（拿不到 → 拒绝启动，单写者守卫）→ 缺失=全新部署 / 损坏或主版本不认=拒绝启动 → 重建插件表、granted、permission-set、domain config → 按 volume_ref 挂载卷 → 服务 RPC。温 realm 惰性创建。

替换算法：停旧进程 → 宿主启动新引擎产物、传入同一 state 路径（命令行/环境）→ 新引擎读同一份数据接着推进（ADR-001）。

原子替换：写临时文件 → rename，单写者，崩溃安全。

#### 7 异常处理与边界条件

| 情形 | 处置 |
|---|---|
| state 缺失 | 全新部署（空启动） |
| state 不可解析 / 主版本不认 | 拒绝启动（fail-safe，绝不静默清空当新库） |
| state 文件锁被占 | 拒绝启动（单写者守卫） |
| 管理 RPC 载荷非法 | JSON-RPC error 对象（不与 invoke 混淆） |
| 传输中断 / 超时 | 按 §7.4 重试语义；引擎无宿主不可自杀 |
| 插件崩溃 | realm 回收，进程存活（故障隔离） |
| 坏卷 | 按 volume_ref 挂载失败 → 该插件置 error 上报，不拖垮整体 |

边界：引擎无内存态依赖（C2/G6）；空闲不主动保活（宿主拉起）。

#### 8 横向关注点

- 安全：本地可信信道（UDS peer 凭据），引擎-宿主间不加密（A1）；攻击面在插件签名面。
- 可靠性：替换不丢数据 = 自洽恢复；state 原子替换崩溃安全。
- 可观测性：两通道，均 engine→host 单向——
  ① 事件流 **notify**：`realmEvicted` / `quarantined(plugin_id)` / `pluginUpdated` / `pluginRemoved`，引擎在状态变更时单播，宿主据此对齐状态视图；不含保密载荷，非请求应答。
  ② **trace** 流式轨迹：四类确定性挂点——入口调用起止 / capability 调用参数与结果 / 每次权限裁决 requested vs granted / 值流转，每条关联调用点（模块+行号）供审计定位；内部为可复用 trace sink，CLI 导出 human 树 + `--json`，交互式调试器预留挂接。
- 性能：大 blob 留引擎内不跨 IPC；JSON-RPC 简单可调试。

不适用（单进程部署，见主文档 §4.3 部署视图；伸缩/依赖服务不涉及）。

#### 10 设计决策

- ADR-001：状态所有权归引擎（替换契约核心、宿主黑盒）
- ADR-002：store 可扩展格式（弱契约，命名空间+字段、只加不改）
- ADR-005：可重算数据不持久化（本体是唯一源，启动按需拆包重建）

#### 11 约束与假设

- C1 平台进程模型（独立进程可行三平台）；C2 宿主按需拉起（本系统不保活）。
- A1 本地信道可信（IPC 不加密是安全的——攻击面不在本地管道）。

#### 12 需求追溯

- G1：可嵌入 / 绝对独立进程 / 自洽恢复 / 可替换
- G6：正确性不依赖内存态
- G10：CLI 与生产行为对齐（单一引擎核心）

#### 13 测试要点

- 原子替换崩溃安全（写中杀进程不损坏）

- notify 事件在状态变更时准确单播；trace 四类挂点 + 模块行号可审计
