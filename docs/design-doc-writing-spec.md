# 设计文档写作规范（项目无关）

版本：v1.0 · 状态：待评审

> 本规范综合 4+1 视图（Kruchten）、C4 模型（Simon Brown）、arc42、IEEE 1016 / ISO/IEC/IEEE 42010、ADR（Architecture Decision Record）实践，提炼为可直接执行的写作标准。适用于任何复杂系统软件项目，与具体技术栈、编程语言、项目领域无关。

---

## 1. 目的与适用范围

- **目的**：让设计文档成为"可评审、可实现、可验证、可演进"的工程契约，而非事后说明。
- **适用**：新系统总体设计、子系统细化设计、跨团队接口契约、重大架构变更。
- **不适用**：代码注释、用户手册、运维手册（另有文档类型）。

---

## 2. 文档分层

| 层 | 内容 | 粒度 | 评审门 |
|---|---|---|---|
| **主设计** | 目标、约束、总体架构、关键决策、分系统索引 | 全系统 | 架构评审 |
| **增补** | 对主设计的修订/新增，冲突时声明优先级 | 变更单元 | 同主设计 |
| **子系统** | 单个子系统的职责、接口、数据、状态机、错误 | 一子系统一篇 | 模块评审 |
| **ADR** | 单个架构决策的背景、选项、决定、后果 | 一决策一篇 | 随变更评审 |
| **术语表** | 全文档统一术语定义 | 全局一份 | 持续维护 |

规则：

- 子系统文档只写本子系统事，不重复主设计；引用主设计用"§X"指针。
- 增补必须声明基线（基于哪一版）与冲突优先级。
- 废弃内容**归档不删除**（另文件 + 顶部弃用声明 + 指向替代文档）。

---

## 3. 必备章节（主设计）

| # | 章节 | 必须回答的问题 | 完成标准 |
|---|---|---|---|
| 1 | 概述与目标 | 解决什么问题？不解决什么？ | 目标可证伪，非目标明确列出 |
| 2 | 约束与假设 | 干系人、硬约束、假设条件 | 每条假设标注"假设"，可被证伪 |
| 3 | 术语表 | 核心名词定义 | 全文档术语一致，无一词多义 |
| 4 | 总体架构 | 分层/分块、数据流向 | 一张总览图 + 组件职责一句话 |
| 5 | 分系统详述 | 每子系统职责/接口/数据/状态/错误 | 见 §5 |
| 6 | 横切面 | 安全、性能、观测、部署、兼容 | 每项有可验证断言，见 §6 |
| 7 | 接口契约 | 模块间 API/格式/协议 | 见 §7，冻结先于实现 |
| 8 | 质量属性场景 | 可测量的验收标准 | 每条含度量 + 条件，见 §6 |
| 9 | 风险与推迟项 | 已知未知、待定点、演进路径 | 每项有负责人/触发条件 |
| 10 | 修订记录 | rev/changelog | 见 §9 |

---

## 4. 三视图规范

同一系统必须分开描述，**禁止挤在一张图里**：

| 视图 | 回答 | 内容 | 图规范 |
|---|---|---|---|
| **静态** | 有什么 | 模块/组件/依赖关系 | 方框 = 职责单元，箭头 = 依赖方向，标注接口名 |
| **动态** | 如何协作 | 关键流程的时序/状态机 | 时序图或状态机，标注触发条件与异常分支 |
| **部署** | 跑在哪 | 进程/机器/网络、数据落点 | 方框 = 运行时单元，标注进程边界与通信协议 |

图规范：

- 每图有编号、标题、一句话说明。
- 图中每个元素在正文中有对应定义；正文提到的每个组件在图中有位置。
- 状态机必须标注：全部状态、全部转移条件、终态、异常出口。

---

## 5. 子系统详述规范（每子系统必备五件套）

1. **职责**：一句话 + 非职责（明确不做什么）。
2. **接口**：公开操作签名、参数/返回值、前置/后置条件、错误码。
3. **数据**：拥有的数据、格式、持久化方式、生命周期。
4. **状态机**：状态、转移、并发语义。
5. **错误**：错误分类、每类的调用方处置、是否可恢复。

---

## 6. 横切面与质量属性规范

### 6.1 横切面清单（逐项回答"本系统如何处理"）

安全、性能、可靠性、观测性、部署、兼容/迁移、容量/配额。

### 6.2 质量属性场景格式（强制）

每条按此格式写，**形容词禁入**（"高性能""安全"等词不出现，或出现时必有度量跟随）：

```text
场景：在 <条件> 下，<刺激> 发生时，
系统 <可观测行为>，度量为 <数值 + 测量方式>。
```

示例：`在单实例、100 并发下，调用 granted 为空的插件能力时，系统返回 PermissionDenied，p99 延迟 < 5ms（本地压测，见 §X）。`

### 6.3 接口契约冻结规则

- 模块间契约（API/格式/协议）在实现前冻结，变更走增补流程。
- 契约含：版本号策略、兼容承诺、废弃流程。
- 示例与伪代码仅示意时必须声明（"命名与形态以实现为准，语义一致即可"）。

---

## 7. ADR 规范

每个重要取舍（影响接口、数据、安全、性能、成本的决定）必须有一篇 ADR，随代码库存放。

### 7.1 格式

```markdown
# ADR-<编号>：<标题>

状态：提议 / 已接受 / 已废弃（+ 替代 ADR 编号）
日期：YYYY-MM-DD
背景：<问题与约束>
选项：
  - A：<方案>（优点 / 缺点 / 成本）
  - B：<方案>（优点 / 缺点 / 成本）
决定：<选 X，因为 …>
后果：<接受的代价、后续约束、需跟进事项>
```

### 7.2 状态机

`提议 → 已接受 →（被替代时）已废弃`。废弃 ADR 保留原文，只改状态并指向替代者。

### 7.3 编号

全局递增，不复用废弃编号。

---

## 8. 术语与命名规范

- 术语表全局一份；新术语在首次出现处定义并回写术语表。
- 一词一义：同一词在全文中含义唯一；近义词出现时明确等价或区分。
- 命名三问（每个新命名必须能回答）：指什么？不指什么？与近似词的区别？
- 禁止事项：同词多义、未定义的缩写、中英文混用同一概念。

---

## 9. 版本与演进规范

- 主文档头含 `日期 + rev + 本次增量一句话 + 状态（待评审/已接受）`。
- 每次内容变更递增 rev，并在修订记录中写清增量。
- 废弃文档：另存归档文件，顶部加弃用声明（指向替代文档），原文保留。
- 子系统拆分后，主文档与子系统文档的对应关系由索引文件维护，变更时同步更新索引。

---

## 10. 评审质量门（Checklist）

评审前作者自查，评审会上逐项确认。任一项不满足即打回：

- [ ] 目标可证伪，非目标明确列出
- [ ] 术语表完整，全文一词一义
- [ ] 三视图齐全且图-文对应（图中有定义，文中有位置）
- [ ] 状态机有全部状态、转移条件、终态、异常出口
- [ ] 每个子系统五件套齐全（职责/接口/数据/状态/错误）
- [ ] 每个重要取舍有 ADR 编号
- [ ] 接口契约已冻结（含版本/兼容/废弃策略）
- [ ] 质量断言全部可测量（无裸形容词）
- [ ] 异常路径有定义（失败时系统处于什么状态、谁负责恢复）
- [ ] 推迟项有触发条件（什么条件下重新启动该议题）
- [ ] 修订记录与 rev 一致

---

## 11. 反模式（出现即打回）

| 反模式 | 说明 |
|---|---|
| 形容词设计 | "高性能、高可用、安全"无度量跟随 |
| 单图包揽 | 静态/动态/部署挤在一张图 |
| 结论无选项 | 只写决定，不写备选与取舍理由 |
| 接口后置 | 先写实现再补契约 |
| 异常缺席 | 只画 happy path，无失败语义 |
| 术语漂移 | 同一词多处含义不同 |
| 删除式演进 | 直接改写/删除旧设计而非增补+归档 |
| 不可验证 | 断言无对应验收方式 |

日期：YYYY-MM-DD（rev N：<本次增量一句话>）
状态：待评审 / 已接受

> 声明：示例仅示意，语义一致即可，具体命名与形态以实现为准。

## 1. 概述与目标（含非目标）
## 2. 约束与假设
## 3. 术语表
